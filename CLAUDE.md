# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Bare-metal Rust firmware for the **Texas Instruments MSP430FR5969** microcontroller dev board. No RTOS, no `std` — this is `#![no_std]` / `#![no_main]` embedded development.

## Build Commands

```bash
# Build (requires nightly toolchain for build-std)
cargo +nightly build

# Flash via DSLite (TI debug server, runs under Rosetta on M-series Macs)
/Applications/ti/ccs2051/ccs/ccs_base/DebugServer/bin/DSLite load \
  -c /Users/davidfalkner/git/MSP430FR5969/MSP430FR5969.ccxml \
  -f /Users/davidfalkner/git/MSP430FR5969/target/msp430-none-elf/debug/pac_consumer

# Flash and run via mspdebug (not currently working — mspdebug is arm64, TI's libmsp430 is x86_64)
# cargo +nightly run

# Check without building
cargo +nightly check

# Run the host-side math tests (NOT on the msp430 target)
cd unit_tests && cargo +nightly test
```

Requires the **nightly** Rust toolchain (for `-Z build-std=core` on the `msp430-none-elf` target). The TI MSP430 GCC toolchain must be installed — the linker path is hardcoded in `.cargo/config.toml`.

## Testing

Most firmware can only be validated on hardware, but pure logic is tested on the host. The pattern: keep the pure arithmetic in a dependency-free file (no PAC/HAL types, `//` not `//!` comments so it can be `include!`d mid-crate), and have the **detached `unit_tests/` crate** (its own `[workspace]` table + `.cargo/config.toml` overriding the target back to the host triple `aarch64-apple-darwin`, with `build-std = ["std"]` to neutralize the inherited `build-std = ["core"]` — and, being outside the workspace, escaping the `panic = "abort"` dev profile that would break libtest) `include!` that real source, one module per subject. Because the tests include the actual shipping source, a bad edit to the math fails them. Current modules:

- `baud` includes `hal/src/baud.rs` and checks `compute_baud`/`ucbrs_lookup` against SLAU367P Table 30-5. The pass/fail criterion is the resulting average bit-timing error (< 2%), since the driver follows the datasheet *procedure* while Table 30-5 lists values from a separate lowest-error search — the two legitimately differ in some rows (mode choice near N≈16, and alternate `UCBRSx` bytes).
- `ticks` includes `hal/src/ticks.rs` (the tick↔time math `Counter` delegates to: `ticks_to_us`/`ticks_to_ns`/`assemble_now32`) and checks exact conversions, the `u64`-widening overflow guard, and the `now32` bit-packing.
- `fram_addr` includes `hal/src/fram_addr.rs` and pins the FRAM region geometry (Info 0x1800/512 B, upper 0x10000/16 KB) plus the overflow-safe `check_bounds`.
- `adc_cal` includes `hal/src/adc_cal.rs` (the math `tlv::AdcCal`/`tlv::RefCal`/`Adc::to_millivolts` delegate to) and checks the SLAU367 temperature interpolation (30/85 °C TLV points, deci-°C, half-away-from-zero rounding), the 1.15 fixed-point gain/offset/REF corrections (unity identity, clamping), and count→mV rounding.
- `rx_queue` includes `hal/src/rx_queue.rs` (the `Cell`-based ISR→main SPSC byte queue `serial`'s RX-interrupt consumers use) and checks FIFO order, the full/empty distinction, drop-newest overflow with the saturating tally, and the u16 free-running indices through 100k wrap cycles. (The Mutex/critical-section discipline around it is firmware-side and untestable on the host.)
- `crc_soft` includes `hal/src/crc_soft.rs` (the software CRC16-CCITT reference model that `hal::crc` re-exports and the `accel_test_runner` fixture compares the CRC16 silicon against) and pins it to the published catalog check values over `"123456789"` (CCITT-FALSE 0x29B1, XMODEM 0x31C3, KERMIT 0x2189, X-25 0x906E), plus incremental-equals-one-shot streaming and the MSB↔LSB bit-reversal identity that the hardware's `CRCDI`/`CRCDIRB` + `CRCINIRES`/`CRCRESR` register pairs implement.
- `comp_ladder` includes `hal/src/comp_ladder.rs` (the Comp_E reference-ladder tap↔millivolt math `comp_e` re-exports and the `comp_test_runner` fixture predicts its sweep flip taps with) and pins the (tap+1)/32 geometry (tap 0 = 1/32 of the source, tap 31 = the full source), nearest-tap rounding in both directions with the round-trip identity, range clamping, and the LaunchPad's expected flip taps (2.0 V → tap 17, 1.2 V → tap 10 at 3.63 V AVCC).
- `mpu_seg` includes `hal/src/mpu_seg.rs` (the FRAM-MPU segmentation math `mpu` delegates to) and pins the border encoding to TI's own example values (`MPUSEGB1 = 0x0480` ⇔ border `0x4800`, i.e. `addr >> 4` with 16-byte alignment enforced, range `0x4400..=0x14000` inclusive at both ends so the outer segments can be emptied), the `MPUSAM` composition to its documented reset value (four × rwx = `0x7777`; RE/WE/XE/VS = 1/2/4/8 per nibble, seg1→seg2→seg3→info walking bits 3:0→15:12), and the borders-belong-to-the-higher-segment lookup.
- `i2c_slave` includes `hal/src/i2c_slave.rs` (the eUSCI_B I2C slave own-address validation/`I2COA0` encoding and the `UCB0IV` decode table `i2c::I2cSlave` delegates to and re-exports) and pins `UCOAEN` = bit 10/`UCGCEN` = bit 15 (encoded 0x48 → `0x0448`, +general-call → `0x8448`), the accepted own-address range 0x08..=0x77 with both spec-reserved blocks rejected (`Reserved`) and >0x7F as `OutOfRange`, and the full header IV table (0x02 AL / 0x04 NACK / 0x06 START / 0x08 STOP / 0x16 RX0 / 0x18 TX0 / 0x1A BCNT / 0x1C CLTO / 0x1E BIT9, secondary-address slots 0x0A..=0x14 grouped, off-table values → `Unknown` rather than misattributed). The IV slots are documentation-pinned only (msp430fr5969.h) — the slave is not yet HW-verified, and the RTCIV experience says vendor IV tables need on-silicon confirmation.
- `capture_math` includes `hal/src/capture_math.rs` (the timestamp-delta→physics math `capture` re-exports: `hz_from_period_ticks`, `duty_permille`, `periods_in_span`, `span_ratio_permille`, `within_permille` — all `u64`-widened, half-away-from-zero rounding, zero-denominator guards) and pins the fixture's own numbers: 1 kHz PWM at a 1 MHz tick (exact + rounding cases), the ACLK crystal spanned by 1 MHz/8 MHz DCO ticks (30.52/244.14 ticks per period — the period-count rounding must absorb a ±5% DCO error), the DCO-vs-crystal ratio in permille, and inclusive tolerance boundaries.
- `rtc_alarm` includes `hal/src/rtc_alarm.rs` (the RTC_B alarm field validation, `AE`-bit register encoding, and match predicate `Rtc::set_alarm` delegates to) and pins the AE bit to bit 7 of each byte register (enabled minute 30 → `0x9E`, disabled fields → `0x00`, value-0-enabled ≠ disabled), the per-field ranges (minute ≤ 59, hour ≤ 23, weekday ≤ 6, day 1..=31, each rejected with its own error), the all-fields-disabled refusal (no `AE` set can never fire), and the AND-of-enabled-fields match semantics with disabled fields as wildcards (`alarm_matches`, the fixture's fire predictor).
- `rtc_tick` includes `hal/src/rtc_tick.rs` (the RTC_B prescaler-tick rate↔register math `Rtc::enable_tick_interrupt` delegates to) and pins the sixteen power-of-two rates to their banks and `RTxIP` codes (first eight = RT0PS dividing the 32768 Hz crystal, last eight = RT1PS dividing RT0PS's 128 Hz output; code *n* = /2^(n+1) of the bank input, per TI's `RT0IP__2..__256`), the 128 Hz/64 Hz seam where a bank-split off-by-one would land, the halving frequency table in half-hertz units (so 0.5 Hz stays integral) with the 256× chain factor between banks, and the truncated microsecond periods (1 Hz → 1_000_000, 16384 Hz → 61).
- `adc_seq` includes `hal/src/adc_seq.rs` (the ADC12_B sequence-of-channels member validation, `ADC12MCTLx` word encoding, and `ADC12CTL3` map-bit derivation `Adc::read_sequence*` delegate to) and pins the MCTL field layout (INCH bits 4:0, **EOS bit 7**, VRSEL nibble at bits 11:8 — a VREF member = `0x0100`), EOS-on-the-last-member-only encoding (the fixture's own 3-member scan → `0x011E`/`0x011F`/`0x009F`), the internal-source constructors (supply = A31 + `BATMAP`, temperature = A30 + `TCMAP`; a *raw* channel 30/31 maps nothing), and the validation (empty / 9-member / short-buffer / channel-32 rejections — the 8-member cap is the `ADC12SHT0x` coverage boundary — plus the `NeedsRef` gate on VREF members through the plain no-`&Ref` read path).

Run with `cd unit_tests && cargo +nightly test` (must be run from inside the directory so its `.cargo/config.toml` takes precedence). The host triple there is `aarch64-apple-darwin`; change it for other hosts. New pure-math files get a new module here, not a new crate.

## Hardware test setups (consumer demos)

The full `hal_integration_tests` host runner (`cd hal_integration_tests && cargo +nightly run` — all default suites in `src/main.rs`, everything except the interactive by-name-only `spi` and `capture_jumper`) **passes and is re-run frequently** as the HiL regression suite; treat a suite failure after a driver change as a regression, not fixture flakiness. Each suite builds and flashes its own fixture binary (`deployment::build_and_flash`), so a full run reflashes the board once per suite.

The `hal_test_runners` demos that exercise eUSCI_B0 each need specific board wiring. **eUSCI_B0 is *either* SPI or I2C** (one register block at 0x0640, shared P1.6/P1.7 pins), so the SPI and I2C demos are **separate binaries** — only one can be flashed at a time. Observe all of them over the UART backchannel: eUSCI_A0 on `/dev/cu.usbmodem11203` @ **9600 8N1** (e.g. `screen /dev/cu.usbmodem11203 9600`; the eZ-FET gates TX on DTR, which `screen` asserts).

- **SPI loopback (`--bin hal_test_runners`, `src/main.rs`):** install a **jumper wire from P1.6 (SIMO) to P1.7 (SOMI)**. The demo `transfer_in_place`s a 6-byte pattern; with the jumper every byte round-trips → solid **GREEN** LED + UART `PASS`. Without it SOMI floats → solid **RED** + `FAIL` (the transfer still completes, proving it doesn't hang). This is the self-contained SPI test — no external device needed. The HiL fixture (`--bin spi_test_runner`, host module `spi_tests`) additionally covers **eUSCI_A1 SPI** in the same flash: a second jumper from **P2.5 (SIMO) to P2.6 (SOMI)** (UCA1CLK = P2.4), with the A1 pattern the bitwise complement of the B0 one so a cross-wired jumper can't pass. The same jumpers then serve a **DMA phase**: B0 re-runs its loopback through `spi::SpiDma` (the `SpiBus` impl paced by an RX+TX DMA channel pair) and A1 through the split-buffer `transfer_dma`, on byte-reversed patterns so a stale buffer can't fake a pass (`SPI B0/A1 DMA OK` verdict lines; all four verdicts HW-verified 2026-07-05). eUSCI_A0 SPI shares all driver code but has no loopback fixture — its SPI pins P2.0/P2.1 *are* the backchannel UART, and the eZ-FET's TX driver on P2.1 would fight a jumper. The suite is interactive (jumper prompts), so the host runner executes it **only when named explicitly**: `cd hal_integration_tests && cargo +nightly run -- spi`.

- **I2C bus scan (`--bin i2c_scan`, `src/bin/i2c_scan.rs`):** P1.6 = **SDA**, P1.7 = **SCL**. **Remove the SPI loopback jumper first** — on P1.6/P1.7 it shorts SDA directly to SCL and no I2C transfer can work. I2C is open-drain, so add **~4.7 kΩ pull-ups** from SDA and SCL to 3V3 (many breakout boards include their own; a BME280 board typically does). The scanner probes 0x08..=0x77 with zero-length writes and reports ACKing addresses; GREEN if any device answers, RED if the bus is empty. Without pull-ups SCL can't be released high, but the driver no longer hangs on that: the hardware clock-low timeout (`UCCLTO`, ~28 ms) plus a ~100 ms software backstop per operation abort each stuck probe, and a bus-clear bit-bang runs at init to free a wedged slave — a pull-up-less full scan finishes in a couple of seconds and reports a clean **RED/FAIL** instead of going dark.

- **BME280 I2C validation:** wire VCC→3V3, GND→GND, SDA→P1.6, SCL→P1.7 (jumper removed, pull-ups present). The BME280 answers at **0x76** (SDO low) or **0x77** (SDO high) — the scanner catches either. Beyond the address probe, the chip-ID register is the natural `write_read` correctness check: `i2c.write_read(addr, &[0xD0], &mut id)` should return **0x60** (BME280's fixed ID), exercising the write→repeated-START→read path that the scanner alone does not.

- **I2C slave register file (`--bin i2c_slave_test_runner`) — HiL strategy pending:** the board as the *device*, not the master. Same bus rules as the scanner (SDA = P1.6, SCL = P1.7, SPI jumper removed, pull-ups present) plus an **external I2C master** — a Raspberry Pi, a second LaunchPad, a USB-I2C dongle, or a bit-banged GPIO master. The fixture is a 16-register pointer-autoincrement register file at **0x48** with a fixed ID byte `0x69` in register 0 (read-only), so `write_read(0x48, &[0x00], &mut id)` from the master exercises address match, RX, the repeated-START turnaround, and TX in one transaction. Emits `I2C_SLAVE_READY addr=0x48` once per idle second until the first transaction, then `i2c wr ptr=P n=N` / `i2c rd n=N` per STOP (reads usually report one extra byte — the eUSCI's speculative TX request, flushed by the driver at STOP; confirming that flush is a primary goal of the eventual HiL test). GREEN toggles per transaction. The slave driver itself is **code-complete but not yet exercised on silicon**.

The remaining demos use **different peripherals than eUSCI_B0**, so they need no bus wiring and do not conflict with the SPI/I2C demos (they can be flashed independently):

- **Timer_B0 PWM (`--bin pwm_fade`, `src/bin/pwm_fade.rs`):** drives ~1 kHz PWM on **TB0.1 = P1.4** and ramps duty 0→100→0 %. Put an **LED + ~330 Ω from P1.4 to GND** (or a scope on P1.4) to see it breathe; the UART prints `duty: N%` and the on-board LEDs show ramp direction (GREEN up, RED down). The driver picks `TB0.n` outputs with **`SEL0=1, SEL1=0`** (secondary function) via `gpio::Pin::into_timer_b_output`; only P1.4(TB0.1)/P1.5(TB0.2)/P1.6(TB0.3)/P1.7(TB0.4) implement `pwm::PwmPin`. **TB0.0 is the period (`TB0CCR0`), not a usable output**; P1.6/P1.7 collide with eUSCI_B0, so the typestate makes PWM-vs-SPI/I2C on those pins an exclusive choice. Clean rails: 0 % parks the pin low and 100 % high via `OUTMOD=0` (no glitch), everything between uses `OUTMOD=7` Reset/Set.

- **Timer_A PWM (`--bin ta_pwm_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- ta_pwm`). `pwm::PwmTimerA` runs the same up-mode/`OUTMOD` machinery on **TA0/TA1** (two outputs per block: TA0.1=P1.0/TA0.2=P1.1, TA1.1=P1.2/TA1.2=P1.3, via `gpio::Pin::into_timer_a_output` — `PxDIR` picks compare-output over capture-input on these pads), so PWM no longer costs TB0 or the P1.6/P1.7 eUSCI_B0 conflict. The observation trick: **`P1IN` reads the pad even while the timer output unit drives it**, so the fixture samples its own PWM out of the input register — no jumper, no second peripheral. Verdicts: TA1.1's period timestamped by the TA0 `Counter` within 2% of `frequency()` (observed 1001 µs at 1 kHz), 25%/75% duties on TA1's two channels sampled in one pass (asymmetric — a transposed channel map or inverted output fails; observed 250‰/750‰), `OUTMOD=0` clean rails (500 samples all-low at 0%, all-high at 100%), TA1.2 unchanged after all the TA1.1 churn (per-channel `CCRn`/`CCTLn` disjointness), and the freed TA0 rebuilt as a **second generator** at 2 kHz/50% (observed 502‰) — instance-genericity on silicon, leaving LED2 glowing half-bright as the alive indicator (no green heartbeat in this fixture; P1.0 *is* the output). All six verdicts HW-verified 2026-07-08. Avoid driving P1.1 (TA0.2) while button S2 could be pressed — S2 shorts the pad to ground.

- **RTC_B calendar (`--bin rtc_clock`, `src/bin/rtc_clock.rs`):** prints `YYYY-MM-DD HH:MM:SS` once per second and blinks GREEN. **Requires the 32.768 kHz LFXT crystal** — the RTC "is clocked by XT1" (datasheet), so the demo uses `clocks::configure_low_power` to start LFXT, and `rtc::Rtc::new` **returns `Error::ClockNot32768` unless `clocks.aclk() == 32768`** (lights RED + prints a refusal). The LaunchPad populates the crystal, so it should run crystal-accurate (check for drift against a watch over a minute). Reads go through `now()`, which gates on **`RTCRDY`** to avoid a torn read across the 1 Hz update. Binary mode (`RTCBCD=0`) so `DateTime` fields are plain integers; the single `RTC` interrupt vector (sources demuxed via `RTCIV`, see `rtc::read_iv`) is available via `enable_event_interrupt`/`enable_second_interrupt` but the demo polls. The self-checking sibling (`--bin rtc_test_runner`, host suite `rtc` in the default set) covers the calendar (load read-back + crystal-vs-DCO 1 Hz cross-check; both HW-verified) **plus the alarm**: the fixture re-sets the clock to seconds before a minute boundary so the minute-granular alarm fires ~4 s later, checking a clean arm, no early latch, the polled `RTCAIFG` latch at the boundary, latch-on-increment-*into*-match only (exactly-once per match), and an `RTCAIE` interrupt whose `read_iv` = **0x06** wakes the part from **LPM3** — all seven verdicts HW-verified 2026-07-07, the run that established the true RTCIV table (the alarm observed at 0x06, exposing the off-by-one-slot values the driver docs had carried unverified).

- **RTC_B prescaler ticks (`--bin rtc_tick_test_runner`):** **no wiring** — hands-free, in the default suite (`cargo +nightly run -- rtc_tick`); requires the LFXT crystal like every RTC fixture. Sub-second crystal-accurate periodic interrupts from the RTC's own divider chain via `Rtc::enable_tick_interrupt(TickRate)` — sixteen power-of-two rates, 16.384 kHz to 0.5 Hz, RT0PS rates demuxing to **RTCIV 0x08** and RT1PS to **0x0A** (both HW-observed 2026-07-08), no Timer_A block spent. Verdicts: 32 ticks of 128 Hz wall-clocked by the SMCLK `Counter` at 250 ms ± 5% (crystal ticks against the DCO yardstick — the calendar fixture's cross-check at sub-second resolution; observed 250.8 ms), the 0x08/0x0A IV identities with zero stray sources, both banks running concurrently (they're independent), a **32 Hz tick waking LPM3** with the tally held at exactly one across 100 further ms — the prescaler re-latches every period, so the ISR must disarm via `rtc::isr_disable_tick_interrupts()` (the capture starvation lesson; at 16.384 kHz a tick lands every 61 µs) — and silence after disarm. All six verdicts HW-verified 2026-07-08. Rate↔bank/`RTxIP`-code math is pure in `rtc_tick.rs`, host-tested (unit module `rtc_tick`).

- **UART RX interrupt echo (`--bin serial_irq_test_runner`):** **no wiring** — uses the same eUSCI_A0 backchannel the observations ride on, but **two-directionally**: the host (or a human in `screen`) sends bytes, the `USCI_A0` ISR queues them through `rx_queue::RxQueue`, and main — woken from **LPM0** per byte — echoes each one **plus one** (`a` → `b`; only the software ISR→queue path can produce `b+1`, a wire loopback can't). Emits `UART_IRQ_READY` once per second until the first byte, and `UART_IRQ_STATS dropped=N errors=M` after each `\n`; the host module (`serial_irq_tests`) asserts a 24-byte pattern echoes `+1` in order with `dropped=0 errors=0`. LPM0, not LPM3, because BRCLK = SMCLK.

- **DMA (`--bin dma_test_runner`):** **no wiring** — hands-free, in the default suite (`cargo +nightly run -- dma`). On-device verdicts cover the software-triggered block moves (`copy_bytes`/`copy_words`, `fill_bytes`' fixed source, `copy_bytes_reversed`'s decrementing destination) and the `DMA` vector: each channel armed software-paced (`arm_single_bytes` + `request`) and fired once, with the ISR's `dma::read_iv()` asserting the exact DMAIV demux (ch0/1/2 → 0x02/0x04/0x06, exactly once each). The host-verified half rides on the fixture's own transport: **every report byte is DMA-paced** (`serial::DmaTx` on channel 0 — the burst arriving intact, including a fixed 36-byte `TXPAT` line, *is* the UART-TX-pacing test), and two RX rounds prove DMA reception: round 1 **arms channel 1 for the whole 16-byte payload *before* announcing `DMA_RX_READY`** (`Rx::start_read_dma` + `is_done` polling with a ~5 s abandon), round 2 (`DMA_RX2_READY`) repeats through the blocking `Rx::read_exact_dma`; each payload is echoed `+1` through the DMA TX path. Two hardware lessons baked into the drivers (both observed 2026-07-05): **(1)** wait for `UCTXIFG` *before* arming a TX-paced channel, then write the priming byte with no re-check — arming while a previous byte is still queued lets its hand-off edge fire the fresh channel, and the CPU primer then races the DMA for TXBUF (transposed/dropped bytes on every burst after the first); **(2)** a CPU poll loop cannot open a 9600-baud stream — `delay_ms(1)` really costs ~3.5 ms (the known Delay overhead) while bytes land 1.04 ms apart, so RXBUF overruns between polls (this killed an earlier go-byte handshake). Arm the DMA first, announce second; the host side must also `clear` the OS serial input backlog before acting on a READY, since a buffered announce can be seconds stale.

- **GPIO port interrupts (`--bin gpio_irq_test_runner` / `--bin button_wake`):** **no wiring** — the LaunchPad buttons are on-board (S2 = P1.1, S1 = P4.5, both short to GND with no external resistor → internal pull-up, press = falling edge). The fixture is hands-free: `PxIFG` is software-settable and a software-set flag traverses the same latch → vector → `PxIV` path as a real edge, so it "presses" both buttons from software and checks the IV demux value (P1.1 → 0x04, P4.5 → 0x0C), the exactly-once firing, and the PxIV auto-clear on PORT1 *and* PORT4; the buttons stay armed, so real presses bump the counts in the `gpio p1=… p4=…` info line. `button_wake` is the human demo: main parks in **LPM4** (`power::enter_lpm4`) and S2/S1 presses — the only thing that can wake a part with every clock stopped — toggle GREEN/RED and print a line per press; it `flush()`es the UART before sleeping because LPM4 stops SMCLK mid-character otherwise.

- **LPMx.5 regulator-off sleep (`--bin lpmx5_test_runner`):** **no wiring** — the *host is the wake source*: the UART RX line is physically P2.1, so with that pad re-muxed to GPIO and armed as a falling-edge wake, any byte the host sends wakes LPM4.5 with its start bit. The byte itself is sacrificed to unpowered silicon (the eUSCI doesn't exist while the core domain is off) — losing it is part of what the test demonstrates. Since every LPMx.5 wake is a **reboot**, the fixture is a state machine persisted in Info FRAM, three lives long: cold boot (handshakes `LPMX5_READY` until poked, so no output is lost before the host opens the port) → arm P2.1, **LPM4.5**; host byte → verify `Lpm5WakeUp` cause + latched wake `P2IFG.1` (delivered only because the pin is re-armed *before* clearing `LOCKLPM5`), set RTC to 00:00:55, minute-event wake, **LPM3.5**; RTC rollover ~5 s later → verify `RTCTEVIFG` survived and `Rtc::attach` reads exactly 00:01:00 (the calendar counted through power-off, then froze at the wake under re-asserted `RTCHOLD`). Emits a framed `LPMX5_TEST_BEGIN`/`END` verdict burst (PIN/RTC/TIME) once per second forever; a reflash or reset-button press latches `ResetPin` and restarts the machine from cold. Host module: `lpmx5_tests` (`cd hal_integration_tests && cargo +nightly run -- lpmx5` — the integration runner takes optional suite-name args; no args = full suite).

- **ADC12 drained by DMA (`--bin adc_dma_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- adc_dma`). The converter free-runs in repeat-single-channel+MSC mode while DMA channel 0 drains 32 `MEM0` results per burst; on-device verdicts: every supply-monitor sample within ±160 counts of half scale (ratiometric — garbage buffers can't fake it), every temperature sample within the 5–60 °C TLV-calibrated window (REF_A 2.0 V), and a polled single conversion afterward proving the driver restored `CONSEQ=0`/`MSC=0`. This fixture is what exposed the **ADC12 DMA-trigger latch erratum** (see the `adc` module notes): without the per-run scrub, only the first burst after reset ever completes — debugged on hardware 2026-07-05 by exactly that signature (first run clean, every re-run stalled with conversions verifiably free-running, on fresh channels too, surviving `ADC12ON` power-cycles).

- **ADC12 sequence-of-channels (`--bin adc_seq_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- adc_seq`). One hardware trigger scans three internal members (`CONSEQ=1` + MSC) with **mixed per-member references** — temperature (vs 2.0 V REF_A), absolute supply (A31 vs REF_A, ×2 = AVCC in the 2900–3700 mV window), ratiometric supply-half (A31 vs AVCC, ~2048 ± 160) — whose count windows are pairwise disjoint, so the verdicts are **order-sensitive**: any MCTLx→MEMx transposition puts temperature counts in a supply window and fails loudly, and a REVERSED scan proves the windows follow the members rather than the register file. The DMA phase drains the same scan through trigger 26 with the *source incrementing* across `MEM0..MEM2` (one transfer per member's completion edge, the final one riding the last member's IFG), and the RERUN verdict repeats it six times across a **deliberately parked trigger latch** (a polled conversion injected mid-loop — the erratum's poison) — establishing whether the `consume_stale_trigger_word` scrub behaves identically when the DMA trigger edges come from a multi-member sequence, the erratum's untested corner. The driver's sequence-DMA wait is **bounded** (`SequenceError::DmaIncomplete`) precisely so a wrong trigger model becomes a FAIL line, not a dark board. SINGLE then proves the `CONSEQ=0`/`MSC=0` restore. **HW-verified** — passing in the frequently re-run default suite (including the RERUN erratum-corner verdict: the scrub holds when the DMA trigger edges come from a multi-member sequence).

- **ADC12 window comparator (`--bin adc_window_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- adc_window`). The comparison happens in silicon: any conversion stored through an `MCTLx` with `ADC12WINC` set latches exactly one of `ADC12HIIFG`/`ADC12LOIFG`/`ADC12INIFG` against the `ADC12HI`/`ADC12LO` thresholds, each with its own `ADC12IER2` enable and `ADC12IV` slot (**0x06 above / 0x08 below / 0x0A within**, per msp430fr5969.h `ADC12IV_*` — the 0x06 slot HW-observed 2026-07-08). The fixture's input is the supply monitor (~2048 by construction), so windows placed around/below/above half scale reach all three outcomes from software: verdicts pin each outcome's flag latching **alone**, `clear_window_flags` + no-leak into a plain (`WINC`-less) read, the IV demux from a one-shot windowed conversion delivered out of **LPM0** (latch-with-GIE-off, `enter_lpm0` delivers), the free-running monitor (`Adc::start_monitor*`, repeat-single-channel+MSC with only *outside* crossings armed) converting for 20 ms without a spurious fire while its accumulated `INIFG` proves it really ran, the monitor's **LPM0 wake landing exactly once** — the crossing re-latches every ~60 µs conversion, so the ISR must disarm via `adc::isr_disable_window_interrupts()` (the capture module's starvation lesson, ADC edition) — and the `CONSEQ=0`/`MSC=0`/`WINC` restore after `stop_monitor`. All eight verdicts HW-verified 2026-07-08. Monitor conversions complete with `ADC12IE0` clear, so they park the DMA-trigger latch like every polled read — the `*_dma` engines' per-run scrub absorbs it.

- **REF_A calibrated temperature & supply (`--bin ref_temp_test_runner`):** **no wiring at all.** Brings the shared reference up at **2.0 V** (one setting serves both measurements: the temp sensor fits under any reference, but AVCC/2 ≈ 1.65 V would clip against 1.2 V) and prints the die temperature in °C — interpolated between the factory 30/85 °C TLV points — plus AVCC in mV via the (AVCC–AVSS)/2 monitor through the full gain→offset→REF-factor calibration chain. Expect a few °C above ambient (die self-heating) and **≈3630 mV** on USB power — the eZ-FET LDO feeds this LaunchPad ~3.6 V, *not* 3.3 V (HW-measured 2026-07-03, confirmed by the fixture's two-reference cross-check: supply re-measured against the 2.5 V reference agrees within 0.3%); GREEN while the on-device plausibility windows (5–60 °C, 2900–3700 mV) and the TLV lookup pass, RED otherwise. Complements `--bin adc_internal_test_runner`, which deliberately leaves REF_A **off** and asserts the temp sensor reads ~0 (the sensor is biased by REF_A, not the ADC).

- **Hardware accelerators, CRC16 + AES256 (`--bin accel_test_runner`):** **no wiring at all** — both modules are pure bus peripherals; hands-free, in the default suite (`cargo +nightly run -- accel`). CRC16 verdicts: the silicon against the host-pinned soft model (`crc_soft.rs`; three byte patterns × seeds 0xFFFF/0x0000 × both bit-order register pairs), the `CRCRESR == bitrev16(CRCINIRES)` cross-check, the word-write fast path, and the four catalog one-shots against **hardcoded** published constants (so a wrong model can't vouch for itself). AES256 verdicts: FIPS-197 appendix-C KATs at all three key lengths, each ciphertext decrypted back (every call crosses the encrypt↔decrypt boundary, exercising the driver's transparent key reload), the SP800-38A CBC-AES128 two-block vector + round trip, and a 48-byte multi-block ECB round trip. All eight verdicts HW-verified 2026-07-05; the run also settled the one byte-order question SLAU367 leaves fuzzy — a `CRCDIRB` **word** write processes the **lower byte first** (word-fed `"12345678"` reads 0x3D14 = lower-first, not 0xA12B = upper-first), so the word path equals the byte path over little-endian (memory-order) serialization.

- **Comp_E analog comparator (`--bin comp_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- comp`). The stimulus is **REFOUT**: `Ref::enable_output` buffers the shared reference onto P1.1 = comparator channel C1, the one way to put a known mid-rail analog voltage on a pad from software (keep button S2 released — it shorts P1.1 to ground). Comparator *edges* are made by **stepping the ladder taps across REFOUT** (`set_taps` — the same mechanism the hysteresis hardware uses). Verdicts: far-tap rail sides, the `CEEX` invariant (exchange swaps terminals *and* inverts the output, so the logical comparison is **unchanged** — asserted at both output states), the `CEIV` demux (rising = 0x02, falling = 0x04, exactly once each, read-auto-cleared), a comparator-edge **LPM0 wake** (edge latched with GIE off, `enter_lpm0` delivers it), and two 32-tap sweeps at 2.0/1.2 V that run the comparator as a manual SAR — monotone masks whose flip taps must land within ±2 taps of the prediction from the ADC-measured AVCC (observed: exactly on, taps 17 and 10 at 3.65 V). All seven verdicts HW-verified 2026-07-05. Two hardware facts the run established: **(1) `CEPD` is required** for a channel to reach the comparator at all (it is the pad→comparator connection enable, not merely the input-buffer disable its name suggests) — the driver sets it on every route; **(2) a pad only reaches the comparator through the analog function** (`PxSEL = 11`), which disconnects the output driver — so the tempting "compare a pad you're digitally driving" fixture trick is physically impossible on this part (the fixture keeps a driven-pad probe as a diagnostic, reported as `dig=0` in its info line).

- **Timer_A input capture (`--bin capture_test_runner`):** **hands-free except one *optional* jumper** — in the default suite (`cargo +nightly run -- capture`), where the two jumper-dependent PWM verdicts may report `SKIP`. Capture timer is **TA1** on SMCLK under `configure_low_power` (SMCLK = 1 MHz, ACLK = LFXT crystal), exploiting TA1's two internal capture inputs (SLAS704G Table 6-14): **`ACLK` on CCI2B** — the crystal timestamped by DCO ticks, span over ~16 periods bracketed by two serviced edges with the period count recovered by rounding (`capture_math::periods_in_span`), ratio gated at ±5% (that verdict *is* the DCO measured against the crystal) — and **`COUT` on CCI1B** — Comp_E edges made with the comp fixture's REFOUT + ladder-tap-step trick, each timestamp asserted inside its `now()` bracket with the `CCI` level readback matching the edge direction (keep S2 released). Also hands-free: the software `CCIS` GND→VCC fire (timestamp-at-event bracket + exactly-once), `COV` latch/clear semantics, the `TA1IV` demux (comparator capture → 0x02 exactly once, ACLK capture → 0x04, overflow → 0x0E, read-auto-cleared, frozen after disarm), and an ACLK-capture **LPM0 wake** (SMCLK stays alive in LPM0; the fixture sleeps *into* a stimulus that is never more than 30.5 µs away). The jumper phase (**P1.4 = TB0.1 PWM out → P1.2 = TA1.CCI1A**, auto-detected by driving P1.4 as GPIO against a pull-down on P1.2): the fixture's own ~1 kHz PWM measured back — frequency within 1% of `Pwm::frequency()` (both timers ride the same SMCLK) and 25%/75% duty within ±2% (asymmetric points, so an inverted or stuck line can't pass). The interactive host variant `cargo +nightly run -- capture_jumper` prompts for the jumper and turns `SKIP` into failure. **Two lessons are baked into the driver:** (1) at MCLK = 1 MHz an ACLK-rate capture ISR costs more than one 30.5 µs period, so a keep-armed handler re-enters back-to-back and starves main forever — one-shot wake handlers must disarm *inside the ISR* via `capture::isr_disable_interrupt`; (2) span bracketing tolerates `COV` by design (every `TAxCCRn` stamp is a genuine edge time, and a span only needs *a* fresh edge at each end), while paired measurements (`wait_edge`/period/duty) treat `COV` as the error it is. **HW-verified** — the hands-free `capture` suite passes in the frequently re-run default set (the jumper-dependent PWM verdicts run via the interactive `capture_jumper`).

- **High-speed clock profiles (`--bin clock_speed_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- clock_speed`). Default build runs `clocks::configure_max_speed` (MCLK = SMCLK = 16 MHz, one FRAM wait state); `--features clock_high_speed` swaps in `configure_high_speed` (SMCLK 16 MHz, MCLK 8 MHz, zero wait states) — one source, both profiles, like `baud_115200`. Verifying a clock change needs signals with different blind spots, since MCLK/SMCLK/BRCLK all scale together off the one DCO: the `FRCTL0.NWAITS` **readback** (password-free read proves the bracketed write landed; code *running* at 16 MHz MCLK is itself the wait-state fetch-path proof), a timer-measured `delay_ms(10)` (the MCLK↔SMCLK ratio + the Delay overhead shrinking from ~2.5 ms at 1 MHz to ~0.2–0.4 ms), the **VLO measured via capture** (ACLK = VLO is DCO-independent, so a DCO stuck in the low range doubles the reading out of the 5–15 kHz gate — also the first capture-as-clock-instrument use on a non-crystal source), an Info-FRAM round-trip at 0x80 (lpmx5 owns 0x60, mpu 0x70), and — the absolute check — the **host wall-clocking the BEGIN→BEGIN burst period** (~1.25 s nominal, 0.9–1.8 s gate; a low-range DCO stretches it to ~2.25 s and garbles the 9600 baud UART besides). Info line carries mclk/smclk/nwaits/d10/vlo/reset-reason. **Both profiles HW-verified 2026-07-08, each under its own default-set suite**: `clock_speed` flashes the default `configure_max_speed` build (observed mclk=16000000 nwaits=1), and `clock_high_speed` rebuilds the same source with the cargo feature and flashes that variant (`clock_speed_tests::run_high_speed` → `build_and_flash_with_features`; observed mclk=8000000 smclk=16000000 nwaits=0) — so the feature profile no longer depends on a manual flash.

- **FRAM MPU (`--bin mpu_test_runner`):** **no wiring at all** — hands-free, in the default suite (`cargo +nightly run -- mpu`). The protected target is the upper FRAM bank (borders at the `0x10000` bank split, so code/`.rodata`/vectors all sit in segment 1 and the fixture can never fence itself off). Because the PUC-on-violation path can only be tested by *taking* the PUC, the fixture is a state machine persisted in Info FRAM at 0x70 (`lpmx5_test_runner` owns 0x60) across a deliberate reboot: the cold life proves write-through before protection, a suppressed write (FRAM unchanged) with the seg3 flag latched (no NMI with `MPUSEGIE` off), exactly-once `SYSNMI` delivery with the exact `SYSSNIV` demux (`sys::read_nmi_iv`; seg3 = 0x10, info = 0x0A) and no refire after the handler's mandatory `mpu::clear_violation_flags()`, the info-segment fence, and write-through again after `disable()` — then arms `Access::rx().reset_on_violation()` and violates. The next life finds `SYSRSTIV` = `ResetReason::MpuSeg3` (that *is* the reset verdict; MPU registers survive the PUC, so it stands enforcement down first), then locks a benign config and probes a raw locked register write — SLAU367 doesn't say whether that's ignored or PUCs, so **both** pass (the second via a third life through the `STATE_LOCK_PROBED` arm; the info line reports which, `lock=ignored`/`puc`). Steady state: the framed 8-verdict `MPU_TEST_BEGIN`/`END` burst once per second; reflash or reset button (BOR-class, which is also the only thing that clears `MPULOCK`) restarts cold. All eight verdicts HW-verified 2026-07-05; the run settled the locked-write question — a password-bracketed register write while `MPULOCK` is set is **silently ignored** (`lock=ignored`, borders unchanged), not a PUC — and confirmed the MPU config and `MPULOCK` survive the violation PUC.

## Architecture

**Workspace layout:**
- `pac/` — Peripheral Access Crate auto-generated by `svd2rust` from `msp430fr5969.svd`. Provides typed register access for all MSP430FR5969 peripherals. This is a ~71K-line generated file — do not manually edit `pac/src/lib.rs`. Owns `memory.x` (MSP430FR5969 memory map) and `device.x` (interrupt vector defaults); both are copied to the linker search path by `build.rs` when the `rt` feature is enabled.
- `hal/` — Hardware Abstraction Layer crate built on top of the PAC. Re-exports `pac`, `embedded_hal`, `embedded_hal_nb`, `embedded_io`, and `embedded_storage`. Passes through `rt` and `critical-section` features to the PAC. Modules: `gpio` (typed pins, `embedded-hal` digital traits; port edge interrupts on input pins — `enable_interrupt(Edge)` etc., ISR-side `gpio::read_iv::<Px>()` whose PxIV read atomically clears the served flag; `gpio::unlock_pins(&p.pmm)` clears the chip-wide `PM5CTL0.LOCKLPM5` I/O latch — call once at boot after pin config or the pads stay high-impedance, and on an LPMx.5 wake re-arm the wake pin's `PxIE` *first*; deliberately not folded into `split()`/`init()` for exactly that ordering), `serial` (eUSCI_A UART, `embedded-hal-nb` + `embedded-io`; `Rx::enable_rx_interrupt` fires the `USCI_Ax` vector per received byte — the ISR consumes RXBUF via `serial::isr_read_byte` into an application-owned `rx_queue::RxQueue`, no hidden HAL buffer, polling path unchanged when the interrupt is off; DMA pacing: `Tx::write_all_dma`/`Rx::read_exact_dma` borrow a `dma::Channel`, and `Tx::with_dma` bonds one into a `DmaTx` implementing `embedded_io::Write`), `rx_queue` (`Cell`-based SPSC byte queue for ISR→main handoff behind a `Mutex`, drop-newest + counted overflow; pure code, host-tested), `spi` (instance-generic 3-pin SPI master over eUSCI_A0/A1/B0 — the `Instance` trait carries base, pin mux, and the one register-map difference, `IFG` at 0x1C on eUSCI_A vs 0x2C on eUSCI_B; safe CPU-halting block copies `copy_bytes`/`copy_words`/`fill_bytes`/`copy_bytes_reversed` — block mode + software `DMAREQ` blocks by hardware construction, so plain slice borrows are sound — plus the unsafe peripheral-pacing primitive `arm_single_bytes`/`wait_done`/`request` that serial/spi build on; `TriggerSource` holds the device trigger table (values from `msp430fr5969.h`: UCA0 RX/TX = 14/15, UCA1 = 16/17, UCB0 = 18/19, ADC12 = 26); completion interrupts share the one `DMA` vector, demuxed by `dma::read_iv()` whose DMAIV read atomically clears the served flag — and because that clear happens in silicon, every thread-mode `DMAxCTL` RMW in the driver is under `critical_section::with`. **Triggers are edge-sensitive** (SLAU367P allows `DMALEVEL` only for external DMAE0), so TX pacing waits for `UCTXIFG` *before* arming and then primes byte 0 with no re-check — arm-then-wait races the CPU primer against the DMA and was observed corrupting output on hardware), `i2c` (eUSCI_B0: `embedded-hal` I2C **master**, plus a native event-pump **slave** — `I2cSlaveExt::into_i2c_slave(SlaveConfig)` answers one validated 7-bit own address (`I2COA0`, `UCOAEN` bit 10, optional general call via `UCGCEN` bit 15; reserved addresses rejected, so own addresses live in the scanner's 0x08..=0x77 range) and `poll()` surfaces `SlaveEvent::{Start{read}, Received, TxRequest, Stop}` in a load-bearing priority order (Received before Start so a repeated START can't reorder the last write-phase byte; Stop before Start for missed-window back-to-back transactions; TxRequest last, gated on an active master-read). Correct at any polling latency because the silicon stretches SCL until RXBUF is read / TXBUF is written; `UCCLTO` stays **off** in slave mode — the "stuck" SCL it flags would be this slave legitimately stretching. The eUSCI requests TX bytes one ahead, so a speculative byte can be parked in TXBUF when the master NACK+STOPs; left there it would lead the next read, so the driver flushes it at Stop via a UCSWRST toggle (config preserved, IE saved/restored). `USCI_B0` vector demux via `i2c::read_iv()` + host-tested `decode_iv` (slot values from msp430fr5969.h — documentation-pinned, **not yet HW-confirmed**; remember RTCIV), ISR side `isr_read_byte`/`isr_write_byte`/`isr_disable_interrupts`, thread side `enable_interrupts(SlaveInterrupts)` under `critical_section::with`; `nack_next_byte` = UCTXNACK flow control, `free()` hands the block back for master/SPI rebuild; pure address/IV math in `i2c_slave.rs`, host-tested, re-exported. **Code-complete, HW verification pending** — fixture `--bin i2c_slave_test_runner`), `adc` (ADC12_B; ratiometric AVCC-referenced reads plus absolute VREF-referenced reads that take `&ref_a::Ref`; non-blocking `start_*` siblings + `enable_conversion_interrupt` fire the `ADC12` vector on completion, collected ISR-side by `adc::read_result()` whose MEM0 read also clears `ADC12IFG0` — either MEM0 *or* `ADC12IV` read clears it, so collect once, don't double-dip; `*_repeated_dma` methods run repeat-single-channel+MSC free-running conversions with a DMA channel draining MEM0 per completion — **ADC12 DMA-trigger erratum, HW-confirmed 2026-07-05 (undocumented; TI E2E #401588): the trigger is a LATCH set by any conversion completing with `ADC12IE0` clear and reset ONLY by an ADC-triggered DMA service; CPU MEM0 reads don't reset it, so one unserviced conversion deafens every later edge-sensitive run on every channel, surviving ADC12ON power-cycles.** The engine scrubs it per run via `dma::Channel::consume_stale_trigger_word`, a one-word level-sensitive dummy transfer that a stuck-high latch fires immediately. `read_sequence*`/`read_sequence_dma*` run a hardware **sequence-of-channels** (`CONSEQ=1` + MSC): several *different* inputs scanned off one trigger into `MEM0..MEMn`, ≤ 8 members (the `ADC12SHT0x` coverage boundary, MEM0–7), each `MCTLx` carrying its own `VRSEL` so one scan mixes ratiometric and absolute members (the `_vref` flavors take the `&Ref` that any VREF member requires); member validation/MCTL encoding/map bits are pure math in `adc_seq.rs`, host-tested, re-exported. The sequence DMA drain walks MEM0..n with the *source incrementing* (one transfer per member's completion edge) behind the same per-run scrub, and its completion wait is **bounded** — a missing edge returns `SequenceError::DmaIncomplete` via `dma::Channel::wait_done_bounded` instead of hanging, because whether the latch/scrub behave identically when the trigger edges come from a sequence is exactly what the `adc_seq` fixture exists to establish. The **window comparator** does threshold checks in silicon: `Window` thresholds (raw counts, `low <= high` enforced) loaded into `ADC12HI`/`ADC12LO` with `ADC12WINC` on MCTL0, one of HI/LO/IN latching per windowed conversion — `read_*_windowed` return `(count, WindowVerdict)` decoded from the flags, `start_monitor*`/`stop_monitor` run the free-running threshold watch (repeat-single-channel+MSC, zero CPU/DMA per sample, `WindowEvents` picking which crossings fire the `ADC12` vector, IV slots 0x06/0x08/0x0A = `IV_WINDOW_ABOVE/BELOW/WITHIN`), and a monitor-waking ISR **must disarm via `adc::isr_disable_window_interrupts()`** — the flag re-latches every conversion. All captures `SCS`-synchronized; `COV` semantics split by purpose — paired reads (`wait_edge`, `measure_period_ticks`, `measure_duty_permille`) error on overcapture, span bracketing (`measure_span_ticks` + the host-tested `capture_math.rs` rounding, re-exported) tolerates it by construction since every stamp is a genuine edge time. CCR1/CCR2/overflow share the `TIMERx_A1` vector demuxed by `capture::read_iv::<T>()` (TAxIV read auto-clears, so thread-mode `TAxCCTLn` RMWs are under `critical_section::with`); **a capture source faster than its own ISR (ACLK at MCLK = 1 MHz) starves main forever if the handler stays armed — one-shot handlers disarm inside the ISR via `capture::isr_disable_interrupt`**), `power` (LPMx entry: `enter_lpm0` for CPU-idle-while-peripheral-works, `enter_lpm3` for clocked sleep, `enter_lpm4` for wait-for-pin-edge; all set GIE atomically with sleeping and need `#[interrupt(wake_cpu)]` handlers to resume — plus the **regulator-off** modes `enter_lpm3_5`/`enter_lpm4_5`, which never return: an LPMx.5 wake is architecturally a BOR reset back into `main`, reported as `sys::ResetReason::Lpm5WakeUp`, with state carried across in FRAM and the pins held by the `LOCKLPM5` latch until software reconfigures and unlocks (re-arm the wake pin's `PxIE` *before* unlocking or its latched wake `PxIFG` is lost). `PMMCTL0` is password-protected like `WDTCTL`, its password byte equally unmodeled by the SVD — the HAL uses byte-wise raw writes; never `modify` it through the PAC), `fram` (`embedded-storage`), `mpu` (FRAM Memory Protection Unit: three main-memory segments with two movable borders — `MPUSEGBx` = address `>> 4`, pure math in `mpu_seg.rs`, host-tested — plus the fixed Info-FRAM segment, each with R/W/X enables and per-segment flag-vs-PUC violation policy; violating accesses are *suppressed* (blocked writes leave FRAM unchanged) and latch `MPUCTL1` flags, escalating to the `SYSNMI` vector under `Config::nmi` (demux via `sys::read_nmi_iv()`; the handler **must** call `mpu::clear_violation_flags()` — SLAU367 doesn't promise the SYSSNIV read clears MPU flags) or to a PUC whose cause lands in `SYSRSTIV` (`sys::ResetReason::MpuSeg1/2/3/Info`); **the PAC has no MPU block** (generated from a pre-MPU SVD revision — the checked-in SVD has it at 0x05A0) and the SVD doesn't model the `MPUPW` password byte anyway, so the driver is raw volatile pointers with the CS/PMM-style byte-lane password bracket: `0xA5` → `MPUCTL0_H` opens all MPU registers, any other value closes, and a write while closed is itself a PUC (`ResetReason::MpuPassword`) — high-byte-only writes leave `MPUENA`/`MPULOCK`/`MPUSEGIE` untouched so flags can be cleared without dropping protection; NMIs are non-maskable, so a violation NMI can re-lock the password bracket under interrupted thread-mode config code — configure before violations are possible; `Mpu::lock()` freezes the register file until **BOR** (a PUC does not unlock it — that asymmetry is the tamper resistance; HW-established 2026-07-05: a register write while locked is silently ignored, not a PUC)), `pwm` (Timer_B0 **and Timer_A** PWM, `embedded_hal::pwm::SetDutyCycle`: `Pwm` = TB0's six channels on P1.4–P1.7; `PwmTimerA<T>` = the same up-mode/`OUTMOD=7`/clean-rail machinery instance-generic over TA0/TA1 via `capture::Instance` — TAx.1/TAx.2 on P1.0–P1.3 through `Pin::into_timer_a_output` (output `PxDIR` picks TAx.n over CCIxA on the same pad), freeing TB0 and the P1.6/P1.7 eUSCI_B0 conflict; consume-by-move keeps PWM-vs-capture-vs-`Counter` per block exclusive; TA1 (P1.2/P1.3, free pins) is the natural PWM block — P1.0 is LED2, and don't drive P1.1 with button S2 pressable), `rtc` (RTC_B calendar; native API — embedded-hal has no RTC trait. `Rtc::attach` is the LPM3.5-wake counterpart of `Rtc::new`: the calendar counts through the sleep, but the wake **re-asserts `RTCHOLD`** — freezing it, contents intact — and **clears the RTC interrupt enables**, so `RTCIV` reads 0 even though the waking `RTCTEVIFG` is still latched (read it via `rtc::event_irq_pending`); `attach` releases the hold — all hardware-observed 2026-07-04. The hardware **alarm** — four byte registers `RTCAMIN/AHOUR/ADOW/ADAY`, each compare value + an `AE` enable in bit 7, compared at every minute increment, firing on the AND of *enabled* fields (the enabled subset picks the recurrence: minute-only = hourly, minute+hour = daily…) — via `Rtc::set_alarm(&Alarm)` (SLAU367 order: clear `RTCAIE` first, write registers, clear `RTCAIFG` *last* so a mid-update partial match can't survive; an all-`None` alarm is rejected as `NoFieldEnabled` since it could never fire) + `enable_alarm_interrupt` (`read_iv` = 0x06 — the RTCIV table is 0x02 ready / 0x04 event / 0x06 alarm / 0x0C osc-fault per TI's msp430fr5969.h `RTCIV_*`, alarm slot HW-observed 2026-07-07) or the polled/post-LPMx.5 free functions `alarm_irq_pending`/`clear_alarm_irq`; validation/encoding math in `rtc_alarm.rs`, host-tested, re-exported. **Prescaler ticks**: `enable_tick_interrupt(TickRate)` taps the hardwired divider chain for sub-second crystal-accurate periodic interrupts — sixteen power-of-two rates 16.384 kHz..0.5 Hz, first eight from RT0PS (RTCIV **0x08**), last eight from RT1PS (**0x0A**), the two banks independent and concurrent; crystal-fed, so ticks wake LPM3. One-shot wake handlers **must disarm inside the ISR** via `rtc::isr_disable_tick_interrupts()` — the flag re-latches every period (61 µs at the fastest tap, faster than a 1 MHz MCLK can leave the ISR). Rate↔bank/`RTxIP` math in `rtc_tick.rs`, host-tested, re-exported), and `watchdog` (WDT_A: pre-`take()` `disable()` free function, `Watchdog` start/feed/stop, `force_reset()` software reset, plus interval-timer mode — `start_interval` turns expiry into a periodic `WDT`-vector interrupt instead of a PUC, `enable_interval_interrupt` RMWs the chip-global `SFRIE1.WDTIE` under the shared-SFRIE1 rule; native API — embedded-hal 1.0 dropped the watchdog traits). The crate-root `hal::init(watchdog::WdtMode)` is the boot front door: watchdog policy (`Hold` / `LeaveRunning` / `Arm { source, interval }` to run boot under a chosen timeout) + `Peripherals::take()` fused in guaranteed order.

- `hal_test_runners/` — Test/experimentation binary that exercises the HAL. Minimal `_start()` entry point.

**Key configuration:**
- `.cargo/config.toml` — Sets `msp430-none-elf` target, enables `build-std = ["core"]`, configures TI GCC linker and `mspdebug tilib` as the runner.
- `pac/memory.x` — Defines **only** the MEMORY regions, named `RAM`/`ROM`/`VECTORS` exactly as msp430-rt's `link.x` requires (no SECTIONS — `link.x` `INCLUDE`s this file and supplies them). RAM at 0x1C00 (2KB), ROM/FRAM at 0x4400 (48KB, ends 0xFF7F), VECTORS at **0xFF90** (the 56-word table — 55 PAC interrupt slots + reset word — must end at 0x10000; msp430-rt `ASSERT`s this). Provided to downstream crates via `pac/build.rs` when the `rt` feature is enabled.

**Runtime model:** Startup is provided by **`msp430-rt`** (pulled in through the PAC's `rt` feature). Its `Reset` handler is the reset-vector entry point: it loads the stack pointer, zeroes `.bss`, copies `.data`, then calls the `#[entry] fn main() -> !`. The watchdog must still be stopped as the first thing in `main` — `let p = hal::init(hal::watchdog::WdtMode::Hold).unwrap()` stops it and then takes the peripherals, in that order by construction (msp430-rt does not touch the watchdog, and `Peripherals::take()` enters a critical section). A custom `#[panic_handler]` loops forever. There is no hand-rolled `_start` / `.reset_vector` static / manual `.bss` loop anymore.

**Stack-pointer init (now handled by msp430-rt):** The MSP430 does *not* set the stack pointer (R1) at reset. This project used to hand-roll a `#[naked]` `_start` whose first instruction was `mov #__stack_top, r1`; msp430-rt's `Reset` now does exactly that (`mov #0x2400, r1`, where 0x2400 = `ORIGIN(RAM) + LENGTH(RAM)`). The failure mode if SP is ever left uninitialized is worth remembering: code runs on whatever garbage R1 holds, *appears* to work intermittently, and corrupts memory differently with every build/reset — it once masqueraded as a UART that hung on its first transmit only sometimes. Verify after any runtime change with `msp430-elf-objdump -d` that **`Reset`** begins with `mov #0x2400, r1` and that the last word of `.vector_table` (0xFFFE) points at `Reset`.

**Linking against the TI runtime libraries:** The link uses msp430-rt's `link.x` (`-C link-arg=-T -C link-arg=link.x`), which msp430-rt's `build.rs` writes to the link search path; `link.x` in turn `INCLUDE`s the PAC-provided `memory.x` (regions) and `device.x` (weak interrupt `PROVIDE`s → `DefaultHandler`). `.cargo/config.toml` also links `libgcc` and the device hardware-multiply library (`libmul_f5`) for the MSP430 EABI runtime routines (`__mspabi_mpyi/mpyl`, `__mspabi_divu/remu`) that `core` references once any multiply/divide/format code is present. Key flags: `-nostartfiles` (msp430-rt, not gcc's crt0, owns `Reset`); `-mcpu=msp430` forces gcc to pick the baseline-ISA `430/` multilib that matches rustc's output (`-mmcu` alone selects the MSP430**X** variant and the link fails with an ISA mismatch); `-Wl,--gc-sections` drops dead code. `abort` (referenced by compiler-builtins' `memcpy`) is provided by each binary so newlib's `libc` (with its syscall stubs) need not be linked.

**FRAM budget:** With only 48 KB of FRAM, an *unoptimized* debug build that does arithmetic pulls in overflow-check panics, which drag in the ~30 KB `core::fmt` engine and overflow FRAM. The workspace `[profile.dev]` therefore sets `opt-level = "s"`, `overflow-checks = false`, and `panic = "abort"` so `cargo +nightly build` (debug) still fits. For the same reason `hal::serial` does not implement `core::fmt::Write` (it would pull `core::fmt::write`); format into a buffer and use `embedded_io::Write::write_all` instead.

## Critical-section support

The `msp430` crate (v0.4.1) with feature `critical-section-single-core` provides the `critical_section::set_impl!` implementation. Acquire saves SR then executes DINT+NOP; release restores GIE only if it was previously set. The `pac_consumer` crate force-links `msp430` (`use msp430 as _`) so these symbols resolve. `Peripherals::take()` works.

Note: the watchdog must be stopped *before* `Peripherals::take()`, since `take()` enters a critical section and the default watchdog timeout is ~32ms. HAL consumers call `hal::init(WdtMode)`, which fuses the watchdog stop and `Peripherals::take()` so the ordering can't be gotten wrong (`hal::watchdog::disable()` remains the underlying free function, usable pre-`take()`); only `pac_consumer` still does the raw `0x015C` write, deliberately, since it exercises the PAC without the HAL. **Never write `WDTCTL` through the PAC field API** (`write`/`modify` on `wdtctl`): the SVD does not model the `WDTPW` password byte, so those produce a wrong-password write and an instant PUC — `hal::watchdog` composes the `0x5A00` key into whole-register writes instead.

## Interrupt conventions

Real ISRs are in use and hardware-verified. The recipe, end to end:

- The binary declares `#![feature(abi_msp430_interrupt)]` (plus `#![feature(asm_experimental_arch)]` if any handler uses `wake_cpu`) and defines handlers with `#[msp430_rt::interrupt] fn NAME()`, where `NAME` is a `pac::Interrupt` variant. The macro validates the name against an `interrupt::NAME` path, which `use hal::interrupt;` (the shim in `hal/src/lib.rs`) satisfies. Handlers get the `msp430-interrupt` ABI (RETI) from the macro; the linker overrides the matching `device.x` weak PROVIDE by symbol name.
- ISR↔main shared state is `static X: critical_section::Mutex<Cell<T>>`, accessed on both sides inside `critical_section::with`. Not `RefCell` — no borrow-panic machinery, and a `Cell` is enough when each side only gets/sets.
- Driver structs own their peripheral, so ISRs use module-level **free functions** backed by `pac::X::steal()` that touch only ISR-facing bits: `timer::clear_overflow_irq()`, `timer::clear_wake_irq()`, `rtc::read_iv()`, `gpio::read_iv::<Px>()`. Prefer `read_iv`-style consumption where the peripheral has an IV register — its read-and-clear is atomic in silicon, immune to the lost-flag RMW hazard.
- Interrupt-enable registers shared between bits/owners (`PxIE`, `PxIES`, `PxIFG`) are only ever RMW'd inside `critical_section::with`; the HAL's `enable_*_interrupt` methods do this internally (which is why the HAL's `critical-section` feature now pulls in the `critical-section` crate proper). GPIO arming order is fixed by SLAU367: program `PxIES`, *then* clear `PxIFG` (an IES write can spuriously latch it), *then* set `PxIE`.
- Nothing fires until GIE is set: either `unsafe { msp430::interrupt::enable() }` for stay-awake code, or the `power::enter_lpm*` entries, which set GIE and the LPM bits in one `bis` (atomic — no wake-lost-in-the-gap). Any ISR that must let `main` resume after `enter_lpm*` is `#[interrupt(wake_cpu)]`; port interrupts latch asynchronously and wake even LPM4.
- **Shared-SFRIE1 rule**: `SFRIE1`/`SFRIFG1` are chip-global (WDTIE next to NMIIE/VMAIE…). No driver owns `pac::Sfr` — touch those registers only via `pac::Sfr::steal()`, only with bit-field `modify`, only inside `critical_section::with`, from thread mode only (`hal::watchdog`'s interval-interrupt methods are the reference implementation). Note the dedicated `WDT` vector auto-resets `WDTIFG` on service, so a `fn WDT()` handler needs no flag work.

## Shortcomings in the PAC crate

- The PAC's `rt` feature now depends on `msp430-rt` 0.4.1 (with its `device` feature); consumers use `#[entry]` from `msp430_rt`. **Two intentional hand-patches to generated code** in `pac/src/lib.rs`, both lost on regeneration (regenerate with the msp430 flavor of svd2rust to get both right at the source):
  1. `svd2rust` emitted the vector-table `Vector` union with `_reserved: u32` (4 bytes — wrong for a 16-bit target; correct msp430 PACs use `u16`). It was dormant while `__INTERRUPTS` got garbage-collected, but msp430-rt KEEPs and places the table, so the doubled width overran the VECTORS region. Patched to `u16`.
  2. The interrupt handler declarations (the `extern` block and `Vector::_handler`) were emitted `extern "C"`; they are patched to `extern "msp430-interrupt"` (with `#![cfg_attr(feature = "rt", feature(abi_msp430_interrupt))]` at the crate root, and the `Vector` union gated on `rt` so the non-`rt` build doesn't need the feature). msp430-rt's `#[interrupt]` macro defines handlers with that ABI (they return with `RETI`, not `RET`) and the linker patches the table by symbol name, so the old mismatch was harmless — but the declared type was a lie; verified byte-identical linker output before/after the patch. Real ISRs exist and are hardware-verified (`timer_test_runner` `TIMER0_A1`, `deep_sleep_test_runner` `TIMER0_A0` with `wake_cpu`).
